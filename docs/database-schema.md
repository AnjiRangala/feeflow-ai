# Database schema

All timestamps are stored as MongoDB dates. Mongoose schema validation is applied at the persistence boundary; request payloads are validated separately.

| Model | Main fields and relationships |
|---|---|
| User | `name`, normalized unique `email`, `phone`, selected-out `passwordHash`, `role` (`parent`, `accounts`, or `counsellor`), optional `studentId`, preferred reminder language, selected-out optional `demoSeedKey`, `isActive`, `createdAt` |
| Student | `studentId`, `name`, `batch`, `centre`, parent phone/email, attendance, test-performance entries, payment-promise history, selected-out optional `demoSeedKey`, `isActive` |
| FeePlan | Unique student reference, integer `totalFeePaise`, `discountPaise`, `netFeePaise`, installment count, installments, selected-out optional `demoSeedKey`, `createdAt` |
| Installment (embedded) | Number, due date, integer `amountPaise` and `paidAmountPaise`, status (`upcoming`, `partially_paid`, `overdue`, `paid`), references to payments |
| Payment | Student and installment references, integer `amountPaise`, unique transaction ID, payment method, status, selected-out optional `demoSeedKey`, paid date |
| MockPaymentOrder | Linked student and parent account, installment reference/number, server-fixed integer amount, unique mock transaction ID, status, expiry, completed payment reference |
| Reminder | Student and installment references, recipient, idempotency key and schedule offset, scheduled date, remaining amount, language/message, delivery status, retry metadata, failure/cancellation reasons, sent date, selected-out optional demo marker |
| Refund | Student reference/name snapshot, server-sourced financial inputs, course policy inputs/version, calculated fee-earned/refundable amounts and assumptions, pending-review/approved/rejected status, creator/reviewer references and timestamps, selected-out optional demo marker |
| CounsellorTask | Student reference/name snapshot, risk score/level, feature snapshot and score breakdown, explanation/recommendation, rules-method/model version, status and unique open-task key, counsellor feedback/reviewer/timestamp, selected-out optional demo marker |
| OtpChallenge | User reference, HMAC OTP digest, expiry, attempt count; short-lived authentication support record |

`User.passwordHash` and the optional demo-seed ownership marker are excluded from query results unless explicitly selected. OTP challenges contain no plaintext OTP. Student identifiers and fee-plan student references are unique. The demo seeder uses insert-only upserts and refuses to change unmarked records at its stable identifiers. All persisted monetary amounts are safe integer paise (100 paise = INR 1); decimal rupee input is converted to paise at the frontend boundary, never used for ledger arithmetic.

The `studentId` fields use the human-readable `Student.studentId` key (for example `STU-0587`), not MongoDB ObjectIds. Embedded installment IDs are MongoDB ObjectIds and are the keys referenced by payments and reminders. Fee plans validate that the installment count and integer installment totals agree with net fee, and that paid totals do not exceed the plan. Payment recording updates the plan and transaction history inside a MongoDB transaction, requiring a replica set or mongos.

Parent mock payment orders are short-lived and scoped to the authenticated parent and their linked student. Order amounts and transaction IDs are generated by the backend. A successful mock settlement stores the payment, links it to the installment, and completes the order in one transaction. The mock flow is disabled in production.

Reminder records are uniquely keyed by instalment, due date, and configured schedule offset. Their status lifecycle is `scheduled` → `sending` → `sent`, `failed`, or `cancelled`; stale in-progress attempts are recovered by the scheduler after `REMINDER_STALE_SENDING_TIMEOUT_MS`. Fee payment transactions cancel pending reminders for fully paid instalments and refresh pending-message balances for partial payments within the same MongoDB transaction. Delivery is through an internal mock provider only; no SMS provider is configured.

Refund calculations snapshot the student's gross course fee and ledger net/paid amounts by default; accounts overrides require a recorded reason and source marker. Course dates, duration, non-refundable charges, and policy version are captured as calculation inputs. The sample pro-rata formula and UTC day-count/rounding assumptions are stored with every report. Refund records are review records only: an accounts-role reviewer may approve or reject one pending calculation, and approval does not issue or record a payment.

Risk tasks contain the feature values used for assessment and the returned explanation so a counsellor can review what triggered a flag. A unique open-task key prevents duplicate active tasks per student. Feedback is an audit record; it does not feed back into or automatically retrain the rules baseline.
